## 1. 상태머신·생애주기

### 갭 1. REASSIGNED 반려 시 이미 커밋된 액션 재분배를 되돌릴지 미정

- 심각도: 높음
- 담당 도메인: E/C/B

1. **시나리오/예시**: 김민지의 휴직 handover #101에서 팀장 박리더가 `결제 모듈 QA` 액션 3건을 이서연에게 재분배하고 중간승인한다. 이때 C 액션의 담당자는 이미 김민지에서 이서연으로 바뀐다. 이후 오너 최현우가 "복귀일 불명확" 사유로 반려한다.
2. **문제**: 문서상 반려는 어느 단계서든 가능하고 작성자 상태는 ACTIVE로 원복된다. 그러나 중간승인 시점에 실제 액션 소유자 커밋이 이미 끝난 뒤라, REASSIGNED 반려가 발생하면 김민지는 ACTIVE인데 업무는 이서연에게 남는다. 재분배를 자동 롤백할지, 반려 후에도 재분배를 유지할지 규칙이 없다.
3. **정할 것**: 옵션 A) REASSIGNED 이후 반려 금지. 옵션 B) 반려 시 C 액션을 원담당자에게 자동 롤백. 옵션 C) 반려해도 액션 재분배는 유지하고 handover만 반려 기록으로 둔다. 권장안: A. 실제 커밋 이후에는 최종승인/취소 별도 플로우로 분리해야 상태가 단순하다.

### 갭 2. 동일 작성자의 중복 신청 허용 범위가 없음

- 심각도: 높음
- 담당 도메인: E/B

1. **시나리오/예시**: 정다은이 2026-09-01부터 2026-09-10까지 휴직 신청을 제출해 WAITING 상태가 된다. 팀장이 아직 처리하지 않았는데 정다은이 다시 2026-09-05부터 2026-09-20까지 휴직 신청을 제출하거나, 퇴사 신청을 추가 제출한다.
2. **문제**: 생성 즉시 WAITING 전환은 정해졌지만, 기존 SUBMITTED/REASSIGNED handover가 있을 때 새 handover를 막을지, 대체할지, 병렬 허용할지 정의가 없다. 병렬 허용 시 한 작성자의 멤버 상태와 액션 재분배가 여러 handover에 의해 경쟁한다.
3. **정할 것**: 옵션 A) 작성자별 활성 handover(SUBMITTED/REASSIGNED)는 1개만 허용. 옵션 B) 휴직 기간이 겹치지 않으면 복수 허용. 옵션 C) 기존 신청을 자동 반려/취소하고 새 신청으로 대체. 권장안: A. 퇴사/휴직은 멤버 생애주기 전이이므로 활성 요청을 단일화하는 편이 안전하다.

### 갭 3. ON_LEAVE 상태에서 퇴사로 전환하는 절차가 없음

- 심각도: 중간
- 담당 도메인: E/B/C/D

1. **시나리오/예시**: 오세훈이 2026-08-01부터 2026-11-30까지 육아휴직으로 ON_LEAVE 상태다. 2026-09-15에 복귀 없이 퇴사를 요청한다. 기존 휴직 handover #77은 FINALIZED이고, 당시 액션 일부는 이미 한지우에게 넘어갔다.
2. **문제**: 문서의 멤버 전이는 ACTIVE→WAITING→ON_LEAVE 또는 DELETED만 다룬다. ON_LEAVE에서 OFFBOARDING 신청을 새로 받을지, 기존 휴직 handover와 연결할지, 휴직 중 유지한 host 회의와 미복귀 상태를 어떻게 처리할지 규칙이 없다.
3. **정할 것**: 옵션 A) ON_LEAVE도 OFFBOARDING 생성 허용, 새 handover로 남은 진행 중 프로젝트 전체를 다시 스냅샷. 옵션 B) 복귀 처리 후 ACTIVE에서 퇴사 신청만 허용. 옵션 C) 휴직 handover를 OFFBOARDING으로 전환. 권장안: A. 실제 인사 흐름에 맞고 기존 휴직 기록을 보존할 수 있다.

## 2. 비동기 레이스

### 갭 4. handover 생성 후 새로 생성되는 AI 액션의 귀속 규칙이 없음

- 심각도: 높음
- 담당 도메인: E/C/A

1. **시나리오/예시**: 김하늘이 2026-08-20 퇴사 handover를 생성한 직후, 2026-08-03 14:00 회의 요약 파이프라인이 늦게 완료되어 `고객사 세금계산서 재발행` 액션을 김하늘 담당으로 새로 만든다.
2. **문제**: handover는 생성 시점 액션만 스냅샷한다. 생성 이후 READY가 된 회의 요약이 퇴사자에게 새 액션을 배정하면 해당 액션은 handover에 포함되지 않는다. 최종승인 시 퇴사자는 삭제되는데 고아 액션이 남을 수 있다.
3. **정할 것**: 옵션 A) WAITING/OFFBOARDING 작성자에게 신규 액션 배정 금지. 옵션 B) 새 액션 생성 시 활성 handover에 자동 편입. 옵션 C) 최종승인 직전 C에서 재조회해 delta를 추가. 권장안: C. 생성 후 발생한 비동기 결과까지 오프보딩 완결성에 포함할 수 있다.

### 갭 5. 요약 PROCESSING 중 퇴사 승인 시 처리 순서가 없음

- 심각도: 중간
- 담당 도메인: E/A/D/B

1. **시나리오/예시**: 박소연이 host인 `8월 정산회의` 녹음이 PROCESSING 상태다. 오너가 박소연의 퇴사를 2026-08-03 16:00에 최종승인하고 D는 host 회의를 삭제한다. 16:03에 A 요약 작업이 READY로 바뀌며 토큰 사용량과 액션을 방출하려 한다.
2. **문제**: 회의 삭제, 요약 완료, 액션 생성, 토큰 기록 사이의 선후관계가 정의되지 않았다. 삭제된 회의에서 나온 요약을 폐기할지, 기록으로 살릴지, 액션 생성만 막을지 불명확하다.
3. **정할 것**: 옵션 A) 퇴사 최종승인 전에 작성자 관련 PROCESSING 작업 완료/취소를 기다린다. 옵션 B) 최종승인은 즉시 진행하되 이후 READY 이벤트는 액션 생성 없이 미터링만 기록한다. 옵션 C) 이후 READY 이벤트를 전부 폐기한다. 권장안: B. 계정 삭제를 지연하지 않으면서 실제 사용된 AI 비용은 보존한다.

## 3. 재분배 대상

### 갭 6. 후임 후보가 0명인 일반 사원 handover의 처리 규칙이 없음

- 심각도: 높음
- 담당 도메인: E/B/C

1. **시나리오/예시**: 개발2팀에는 일반 사원 윤태민 1명과 팀장만 있다. 윤태민이 `API 응답 표준화` 미완료 액션 5건을 가진 채 퇴사를 신청했지만, `findReassignCandidates(teamId, excludeMemberId)` 결과가 빈 목록이다.
2. **문제**: 일반 사원은 팀원이 재분배 대상이라고 정해졌지만 후보가 없을 때 팀장에게 배정 가능한지, 다른 팀으로 넘길 수 있는지, 오너 예외 승인이 가능한지 없다. UI는 DnD할 대상이 없어 complete가 막힌다.
3. **정할 것**: 옵션 A) 후보 0명이면 팀장에게 임시 배정 허용. 옵션 B) 오너가 다른 팀/팀장에게 예외 배정. 옵션 C) 조직에서 먼저 팀원을 추가해야 handover 진행. 권장안: A. 같은 팀 책임선을 유지하면서 교착을 피한다.

### 갭 7. 후임 후보의 상태와 예정된 이탈을 검사하는 기준이 없음

- 심각도: 중간
- 담당 도메인: E/B

1. **시나리오/예시**: 팀장 박리더가 김민지의 `정산 배치 모니터링` 액션을 이서연에게 넘기려 한다. 이서연은 현재 ACTIVE지만 이미 2026-08-09부터 휴직 handover가 SUBMITTED 상태다. 액션 마감은 2026-08-12다.
2. **문제**: 후보 목록은 같은 팀과 작성자 제외, actionCount만 정의한다. 후보가 WAITING/ON_LEAVE/곧 퇴사 예정인 경우 제외할지, 마감일과 휴직 시작일을 비교할지 규칙이 없다.
3. **정할 것**: 옵션 A) ACTIVE인 후보만 허용. 옵션 B) ACTIVE라도 후보의 예정 휴직/퇴사 기간과 액션 마감이 충돌하면 제외. 옵션 C) 경고만 표시하고 팀장 판단에 맡김. 권장안: B. 재분배 직후 다시 handover가 필요한 순환을 줄인다.

### 갭 8. 인계할 액션 0건 handover의 승인 플로우가 제품적으로 미정

- 심각도: 중간
- 담당 도메인: E/FE/B

1. **시나리오/예시**: 신입 사원 강유나가 입사 3일 만에 퇴사하고 진행 중 프로젝트 액션이 0건이다. handover #140은 항목이 비어 있어 팀장 화면에 재분배할 카드가 없다.
2. **문제**: 테스트상 0건은 `isAllReassigned=true`라 중간승인이 가능하지만, 제품 규칙으로 자동 중간승인할지, 팀장 확인을 요구할지, handover 자체를 생략할지 문서에 없다. 팀장/오너 화면의 버튼 상태도 달라진다.
3. **정할 것**: 옵션 A) 0건도 handover 생성 후 팀장 확인과 최종승인을 거친다. 옵션 B) 생성 즉시 REASSIGNED로 자동 전이. 옵션 C) E handover 없이 B offboard만 진행. 권장안: A. "업무 없음"도 감사 가능한 승인 기록으로 남긴다.

## 4. 스냅샷·데이터 정합

### 갭 9. 스냅샷 후 원본 액션 상태 변경 시 커밋 기준이 없음

- 심각도: 높음
- 담당 도메인: E/C

1. **시나리오/예시**: 2026-08-03 10:00에 최지훈의 퇴사 handover가 `고객 온보딩 자료 작성` 액션을 TODO로 스냅샷한다. 10:30에 최지훈이 직접 액션을 DONE으로 완료한다. 11:00에 팀장이 이 액션을 김나래에게 재분배하고 complete를 누른다.
2. **문제**: 패키지는 스냅샷을 불변 기록으로 쓰지만, complete 시 C의 현재 액션 상태를 다시 확인하는 규칙이 없다. 이미 완료/삭제/담당자 변경된 액션에 `reassign(actionId, from, to)`를 호출할 때 성공, no-op, 실패 중 무엇인지 미정이다.
3. **정할 것**: 옵션 A) complete 직전 C가 원본 상태를 검증하고 불일치 항목을 실패로 반환. 옵션 B) 스냅샷 기준으로 무조건 커밋. 옵션 C) 완료된 항목은 자동 기록용으로 전환하고 미완료만 커밋. 권장안: A. C 원본과 E 스냅샷의 차이를 사용자에게 드러내야 조용한 오배정을 막는다.

### 갭 10. 휴직 선택 액션 목록의 누락·초과 입력 처리 규칙이 없음

- 심각도: 중간
- 담당 도메인: E/C/FE

1. **시나리오/예시**: 이다영이 휴직 신청에서 액션 id `[201, 202, 999]`를 선택해 보낸다. C가 반환한 handoverable action은 201, 202뿐이고 999는 이미 삭제되었거나 타인 액션이다.
2. **문제**: 현재 서비스는 C 반환 목록을 selectedActionIds로 필터링하므로 999를 조용히 무시한다. 사용자는 3개를 넘겼다고 생각하지만 handover에는 2개만 저장된다. 반대로 selectedActionIds가 null/빈 배열이면 0건 handover가 만들어진다.
3. **정할 것**: 옵션 A) 선택 id와 실제 스냅샷 id가 다르면 생성 실패. 옵션 B) 없는 id는 경고로 내려주고 가능한 것만 생성. 옵션 C) 조용히 무시. 권장안: A. 신청 시점 입력 오류는 조기 실패가 가장 명확하다.

### 갭 11. 회의 히스토리 라이브 조회 실패 시 패키지 응답 정책이 없음

- 심각도: 중간
- 담당 도메인: E/D

1. **시나리오/예시**: handover item 3개가 sourceMeetingId 701을 갖고 있고 sourceMeetingTitleSnap은 `보안 점검 회의`다. 퇴사 최종승인 이후 D가 host 회의 삭제 정책으로 meeting 701을 삭제했다. 오너가 퇴사 패키지 §5를 조회한다.
2. **문제**: 회의는 스냅샷 예외로 라이브 조회한다고 되어 있다. D가 null/404를 반환하면 전체 패키지를 실패시킬지, 해당 회의만 제외할지, 스냅샷 제목만 표시할지 정해져 있지 않다.
3. **정할 것**: 옵션 A) 회의 1건 실패 시 패키지 전체 실패. 옵션 B) 실패 회의는 `deleted/unavailable` 상태로 표시하고 나머지 응답. 옵션 C) sourceMeetingTitleSnap만 사용해 대체 카드 생성. 권장안: B. 감사 화면은 열려야 하고 삭제 사실도 숨기지 않는 편이 낫다.

## 5. 권한·역할

### 갭 12. 최종승인 호출자의 정체성과 권한 검증 계약이 없음

- 심각도: 높음
- 담당 도메인: E/B/FE

1. **시나리오/예시**: ADMIN 권한을 가진 남궁현이 `/api/handovers/88/finalize`를 호출한다. 같은 회사 ADMIN인지, 오너인지, 해당 팀의 권한 범위가 있는지, 본인 퇴사 건인지 요청 객체에는 정보가 없다.
2. **문제**: 설계에는 오너·어드민 최종승인이라고 되어 있지만, 현재 usecase는 `handoverId`와 `finalizedAt`만 받는다. 감사에 최종승인자 스냅샷도 없고 권한 판정 주체도 없다. API가 붙을 때 B auth와 E 상태 전이의 책임 경계가 모호하다.
3. **정할 것**: 옵션 A) 컨트롤러/B auth가 권한을 검증하고 E에는 approverId/name을 넘겨 감사 저장. 옵션 B) E가 OrgQueryPort로 권한을 직접 검증. 옵션 C) 권한 검증은 스코프 아웃하고 상태만 바꿈. 권장안: A. 권한 소유는 B에 두되 E 감사에는 최종승인자를 남겨야 한다.

### 갭 13. 오너 본인 퇴사 최종승인자가 없음

- 심각도: 높음
- 담당 도메인: E/B

1. **시나리오/예시**: 회사 오너 최현우가 본인 퇴사를 신청한다. 회사에는 ADMIN 박서진이 있지만 오너보다 상위 승인자는 없다. 최현우 본인이 자신의 계정 soft delete를 최종승인할 수 있는지도 정해져 있지 않다.
2. **문제**: 최종승인 주체는 오너·어드민이라고만 되어 있다. 오너 본인의 퇴사는 자기승인 허용 여부, 다른 ADMIN 위임, 회사 소유권 이전 선행 조건이 빠져 있다.
3. **정할 것**: 옵션 A) 오너 본인 퇴사는 다른 ADMIN 1명 이상이 최종승인. 옵션 B) 회사 소유권 이전 완료 전에는 오너 퇴사 금지. 옵션 C) 오너 자기승인 허용. 권장안: B. 계정 삭제와 회사 소유권 상실이 연결되므로 B 조직 규칙 선행이 필요하다.

## 6. 동시성

### 갭 14. 관리자 경합 시 낙관적 락/멱등 응답 규칙이 없음

- 심각도: 높음
- 담당 도메인: E/B/C

1. **시나리오/예시**: 팀장 박리더와 오너 최현우가 같은 handover #55 화면을 열어 둔다. 박리더가 10:00:01에 complete를 누르고, 오너가 stale 화면에서 10:00:02에 reject를 누른다. 또는 오너와 ADMIN이 동시에 finalize를 누른다.
2. **문제**: JPA 엔티티에 version 필드가 없고 상태 갱신 충돌 처리 규칙도 없다. 두 트랜잭션이 같은 이전 상태를 보고 외부 포트 호출까지 수행하면 액션 재분배, 멤버 상태 전환, handover 상태가 마지막 저장에 의해 뒤집힐 수 있다.
3. **정할 것**: 옵션 A) handover에 version 기반 낙관적 락을 두고 두 번째 요청은 409로 실패. 옵션 B) DB 상태 조건부 update로 전이별 compare-and-set. 옵션 C) 외부 포트를 멱등으로 만들고 마지막 요청 우선. 권장안: A. 상태머신 기반 도메인에는 충돌을 명시적으로 실패시키는 편이 명료하다.

### 갭 15. 같은 항목을 두 팀장이 동시에 재배정할 때 최종 담당 기준이 없음

- 심각도: 중간
- 담당 도메인: E/B/FE

1. **시나리오/예시**: `법인카드 영수증 정리` 액션을 박리더는 이서연에게, 권리더는 장민호에게 거의 동시에 DnD한다. 두 요청 모두 SUBMITTED 상태를 보고 저장을 시도한다.
2. **문제**: 재배정은 항목 단위로 덮어쓰기 가능하지만 누가 마지막으로 바꿨는지, stale 보드 변경을 막을지, 재배정 이력을 남길지 없다. 팀장 화면에서 보던 후보 actionCount도 즉시 낡는다.
3. **정할 것**: 옵션 A) handover version으로 stale 재배정을 거부. 옵션 B) item별 updatedAt/version을 두고 해당 카드만 충돌 처리. 옵션 C) 마지막 저장 우선. 권장안: A. 현재 aggregate 단위가 handover이므로 전체 보드 version으로 처리하는 것이 단순하다.

## 7. 오프보딩 완결성

### 갭 16. 삭제된 회원이 다른 handover의 후임으로 지정된 경우 처리 규칙이 없음

- 심각도: 높음
- 담당 도메인: E/B/C

1. **시나리오/예시**: 이서연은 김민지 휴직 handover #201의 후임으로 `배포 체크리스트 점검`을 받을 예정이다. handover #201은 SUBMITTED 상태다. 그런데 이서연 본인의 퇴사 handover #202가 먼저 FINALIZED되어 이서연 계정이 soft delete된다.
2. **문제**: 후임 스냅샷은 E handover item에 남아 있지만, 실제 커밋 시 C 액션을 삭제 회원에게 넘길 수 있다. 후임이 삭제/휴직/권한상실 상태가 되었을 때 기존 handover 항목을 자동 미배정으로 되돌릴지 규칙이 없다.
3. **정할 것**: 옵션 A) B offboard 시 E가 해당 memberId를 reassignee로 가진 활성 handover를 무효화/미배정 처리. 옵션 B) complete 직전 후임 상태를 재검증해 실패. 옵션 C) 삭제 회원에게도 기록상 재분배 허용. 권장안: B. 최종 커밋 직전에 막으면 B→E 역방향 이벤트 없이도 일관성을 확보할 수 있다.

### 갭 17. offboard 외부 처리 일부 실패 시 완료 판정이 없음

- 심각도: 높음
- 담당 도메인: E/B/D/C

1. **시나리오/예시**: 오너가 박소연 퇴사를 최종승인한다. E는 FINALIZED로 바꾸고 B `offboard(박소연)`을 호출한다. B는 권한 회수는 성공했지만 D host 회의 삭제 요청 중 2건이 실패하거나 감사 로그 저장이 실패한다.
2. **문제**: 계약은 "soft delete + 권한·자원 회수 잔여 0 감사"를 말하지만, B/D/C에 걸친 부분 실패를 E 상태에 어떻게 반영할지 없다. E가 FINALIZED로 저장되면 화면상 퇴사가 끝났는데 잔여 자원이 남을 수 있고, 반대로 외부 작업 성공 후 E 저장 실패 시 재시도 멱등성이 필요하다.
3. **정할 것**: 옵션 A) B `offboard`가 내부적으로 모든 회수/삭제를 완료하거나 실패를 던지는 단일 멱등 오케스트레이션을 제공. 옵션 B) E에 OFFBOARDING_PROCESSING 같은 보상 상태를 추가. 옵션 C) 실패해도 FINALIZED로 두고 별도 운영 알림. 권장안: A. E 상태머신을 늘리지 않고 B가 계정 종료 원자성을 책임지는 계약이 문서 방향과 맞다.

## 8. 토큰 미터링

### 갭 18. 쿼터 체크와 실제 토큰 기록 사이 예약/초과 정책이 없음

- 심각도: 높음
- 담당 도메인: A/B/F

1. **시나리오/예시**: 루나텍 회사의 월 상한은 100,000 tokens이고 현재 99,000 tokens를 사용했다. 2026-08-03 13:00에 회의 요약 3개가 동시에 시작되며 각 작업이 `canConsume(companyId)=true`를 받는다. 완료 후 각각 2,000 tokens를 기록하면 총 105,000 tokens가 된다.
2. **문제**: 설계의 `canConsume`은 누적 < 상한만 확인한다. 실행 전 예상 토큰 예약, 동시 실행 락, 초과 허용량이 없으면 hard limit을 초과한 사용이 정상 기록된다.
3. **정할 것**: 옵션 A) 작업 시작 시 예상 토큰을 reserve하고 완료 시 actual로 정산. 옵션 B) 동시 실행 수를 제한하고 완료 후 초과분은 overage로 표시. 옵션 C) hard limit은 best-effort로 보고 초과 허용. 권장안: A. hard limit을 제품 기능으로 말하려면 예약 원장이 필요하다.

### 갭 19. 실패·취소·재시도된 요약의 토큰 비용 귀속이 없음

- 심각도: 중간
- 담당 도메인: A/F

1. **시나리오/예시**: `주간 영업회의` 요약 job-777이 모델 호출에서 3,200 input tokens와 500 output tokens를 사용한 뒤 DB 저장 실패로 FAILED가 된다. 사용자가 재시도해 job-778은 성공하고 4,000 tokens가 기록된다.
2. **문제**: 문서에는 성공 READY 시 1회 기록만 있다. 실패했지만 실제 API 비용이 발생한 토큰을 버릴지, 내부 원가로만 기록할지, 고객 쿼터에 차감할지 미정이다. 재시도 jobId가 달라지면 같은 회의에 비용이 여러 번 쌓일 수도 있다.
3. **정할 것**: 옵션 A) READY 성공분만 고객 쿼터 차감, 실패분은 내부 운영 원장에 별도 기록. 옵션 B) 실제 API 호출 비용은 실패해도 고객 쿼터 차감. 옵션 C) 실패분은 완전히 미기록. 권장안: A. 사용자에게 제공되지 않은 결과를 고객 쿼터에서 빼지 않되 원가 분석은 가능해야 한다.

### 갭 20. 월 경계·부서 이동 시 사용량 귀속 기준이 없음

- 심각도: 중간
- 담당 도메인: A/B/F

1. **시나리오/예시**: 2026-08-31 23:59에 생성된 회의 요약이 2026-09-01 00:03에 READY가 되고 토큰 6,500개를 기록한다. 회의 host 한지우는 9월 1일자로 개발팀에서 플랫폼팀으로 이동했다.
2. **문제**: `recorded_at` 기준 월 합산은 정해졌지만, 회의 발생 시각과 요약 완료 시각이 월 경계를 넘을 때 어느 달에 귀속할지 없다. teamId도 이벤트 방출 시점의 현재 팀인지 회의 당시 팀인지 미정이다.
3. **정할 것**: 옵션 A) READY/recorded_at 기준 월과 당시 전달받은 teamId로 귀속. 옵션 B) meeting date 기준 월과 회의 생성 당시 teamId로 귀속. 옵션 C) 비용은 recorded_at, 대시보드 분석은 meeting date로 이중 축 제공. 권장안: B. 회의 기반 비용 리포트라면 실제 업무 발생 시점과 조직을 기준으로 보는 것이 관리자가 이해하기 쉽다.
