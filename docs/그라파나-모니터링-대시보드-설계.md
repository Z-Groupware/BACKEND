# 그라파나 모니터링 대시보드 설계

- 작성일: 2026-08-12
- 이슈: [#399](https://github.com/Z-Groupware/BACKEND/issues/399)
- 배경: 팀 요청(태완님) — 로그 텍스트 뷰 패널, 로그 유입량 그래프 패널 추가. 목적은 장애/에러 실시간 감지 + 팀 발표용 데모.
- 전제: 로그 파이프라인(Backend Promtail → Loki)은 이미 완료·검증됨 (`백엔드_로그_모니터링_Loki_Promtail_인수인계.md` 참조). 이번 설계는 그 다음 단계 — Prometheus 메트릭 연동 + Grafana 대시보드 구성 + 알림.

## 1. 목적

1. 장애/에러 실시간 감지 (Slack 알림 포함)
2. 팀 발표/데모용 — 모니터링 체계를 갖췄다는 것을 한 화면에서 보여줌

## 2. 아키텍처 / 데이터 흐름

```
Spring(z-spring) --/actuator/prometheus--> Prometheus (Monitoring EC2, scrape)
Redis(z-redis)   --redis_exporter(신규)--> Prometheus
Backend Promtail --(기존, 완료)--------> Loki (Monitoring EC2)

Grafana (Monitoring EC2)
  ├─ Loki 데이터소스 조회        → 대시보드 A (로그)
  ├─ Prometheus 데이터소스 조회  → 대시보드 B (메트릭)
  └─ Grafana Alerting (내장)     → Contact Point: Slack Webhook
```

핵심 변경 3가지:
1. `z-spring`에 `/actuator/prometheus` 노출 — Nginx 레벨에서 외부 공개는 그대로 차단 (기존 원칙 유지)
2. `redis_exporter` 컨테이너 신규 추가
3. Monitoring EC2 Prometheus target에 위 둘 등록

## 3. 컴포넌트별 변경

### Spring
- `micrometer-registry-prometheus` 의존성 추가, `/actuator/prometheus` 활성화
- 인증 없이 열되 Nginx에서 외부 공개 차단 (SG로만 Monitoring EC2 접근 허용)
- **컨벤션**: 우리(action/project) BC가 아닌 다른 BC 클래스에 메트릭 코드를 심어야 할 경우, 클래스 위에 한 줄 주석으로 "메트릭 수집을 위해 추가됨" 등 이유를 명시한다

### Redis
- `oliver006/redis_exporter` 이미지를 `infra/docker-compose.yml`에 신규 서비스로 추가 (EC2 수동 작업 아님, 코드로 바로 반영)

### Monitoring EC2 — Prometheus
- `prometheus.yml`에 Spring(`:8080/actuator/prometheus`), redis_exporter(`:9121`) target 등록
- Backend EC2 SG에 Monitoring SG를 소스로 하는 인바운드 규칙 추가 (8080, 9121)

## 4. 대시보드 A — 로그

**패널 1: 로그 텍스트 뷰**
- Logs 패널, Loki
- 기본 쿼리: `{container=~"z-spring|z-redis"}`
- `container` 변수로 필터링 가능
- 에러 전용 보조 쿼리: `{container="z-spring"} |~ "(?i)error|exception|failed"`

**패널 2: 로그 유입량 그래프**
- Time series, Loki
- 쿼리: `sum by (container) (count_over_time({container=~"z-spring|z-redis"}[1m]))`
- 급증 구간 시각 임계선 표시 (알림 아님, 시각 표시만)

## 5. 대시보드 B — 메트릭

**HTTP 상태 (Spring)**
- 5xx/4xx 에러율: `sum(rate(http_server_requests_seconds_count{status=~"5.."}[1m])) / sum(rate(http_server_requests_seconds_count[1m]))`
- 응답시간 p95: `histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket[1m])) by (le))`
- TPS: `sum(rate(http_server_requests_seconds_count[1m]))`

**JVM/리소스 (Spring)**
- 힙 사용률: `sum(jvm_memory_used_bytes{area="heap"}) / sum(jvm_memory_max_bytes{area="heap"})`
- GC 시간: `rate(jvm_gc_pause_seconds_sum[1m])`
- CPU: `system_cpu_usage`
- 스레드 수: `jvm_threads_live_threads`

**Redis (redis_exporter)**
- 커넥션 수: `redis_connected_clients`
- 메모리 사용률: `redis_memory_used_bytes / redis_memory_max_bytes`
- 커맨드 처리량: `rate(redis_commands_processed_total[1m])`

## 6. 알림 (Grafana Alerting → Slack)

Contact Point: Slack Webhook 1개.

| 규칙 | 조건 | 지속시간 |
|---|---|---|
| 5xx 에러율 급증 | > 5% | 1분 |
| 힙 메모리 위험 | > 85% | 5분 |
| Redis 메모리 위험 | > 80% | 5분 |

값은 업계 표준값으로 시작, 운영하면서 오탐/미탐 보고 튜닝. 로그 유입량은 알림 대상 아님(시각화만).

Slack Webhook URL은 하드코딩 금지 — 기존 `infra/deploy.sh`의 SSM Parameter Store 패턴을 따라 주입.

## 7. Dashboard as Code — 저장 구조

```
infra/
├── docker-compose.yml          # redis_exporter 서비스 추가 (기존 파일 병합)
├── deploy.sh
└── monitoring/                 # 신규
    ├── prometheus/
    │   └── prometheus.yml
    └── grafana/
        ├── provisioning/
        │   ├── datasources/datasources.yml
        │   └── dashboards/dashboards.yml
        └── dashboards/
            ├── logs-dashboard.json      # 대시보드 A
            └── metrics-dashboard.json   # 대시보드 B
```

대시보드는 Grafana UI에서 만든 뒤 JSON Export → 이 경로에 커밋. Provisioning이 컨테이너 기동 시 자동 로드.

`.gitignore`의 `*.md` 전역 무시 규칙 때문에 이 문서 자체는 `git add -f`로 강제 추가 필요 (공용 `.gitignore`는 건드리지 않음).

## 8. Monitoring EC2 반영 방식 (모성진 확인 완료, 2026-08-12)

- 현재 `/opt/monitoring/`(compose, `prometheus/prometheus.yml`, `loki/`)는 별도 배포 스크립트나 관리 레포 없이 EC2에서 직접 관리 중. 팀원이 직접 수정 가능
- Grafana·Prometheus·Loki 데이터는 Docker named volume으로 영속화 — **`docker compose down -v`는 절대 사용 금지** (볼륨 삭제됨)
- 이번 작업부터 원본을 이 레포(`infra/monitoring/`)로 옮기고, 반영은 다음 순서로 진행:
  1. 작업 전 EC2에서 백업
     ```bash
     cd /opt/monitoring
     sudo cp docker-compose.yml "docker-compose.yml.bak-$(date +%Y%m%d-%H%M%S)"
     sudo cp prometheus/prometheus.yml "prometheus/prometheus.yml.bak-$(date +%Y%m%d-%H%M%S)"
     ```
  2. 레포에서 수정한 설정을 EC2에 반영하기 전 문법 검증
     ```bash
     cd /opt/monitoring
     sudo docker compose config -q
     ```
  3. 이상 없으면 적용
     ```bash
     sudo docker compose up -d
     sudo docker compose ps
     ```
- 비밀값(Slack Webhook URL 등)은 레포에 올리지 않고 EC2 또는 SSM Parameter Store에서 관리 (기존 `infra/deploy.sh` 패턴과 동일)

## 9. 남은 후속 확인

- 알림 임계값은 표준값으로 시작 — 운영 데이터 쌓이면 재조정 필요
- Redis exporter의 Backend EC2 SG 인바운드 규칙 추가는 AWS 콘솔 작업 필요 (코드로 안 됨, 별도 수행)
