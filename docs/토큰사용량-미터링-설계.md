# 토큰 사용량 미터링 — 설계 (박종준 심화 조각)

> ⏳ **설계 시점 스냅샷 (2026-08-06 보존)** — 이 문서는 E 모듈 설계·기획 과정의 기록이며 최종 구현이 아니다. 예외 정책·상태 enum·응답 필드·경계식 등 실제 계약은 그 뒤 `develop` 코드에서 확정됐다. **정본은 항상 `develop`의 코드**이며, 문서와 코드가 다르면 코드가 옳다.

> 2026-08-03 · 발표 기술 차별점. 스코프=**미터링 + 쿼터 + 대시보드** (실결제 Toss 제외).
> 위치=용량/사용량(ST) 확장 — 기존 "녹음 GB"에서 "AI 토큰"까지.

## 0. 차별점 (한 줄)
그룹웨어 과금 = 100% seat + 스토리지 GB. 잇다 = **AI 토큰 사용량(실제 원가) 기반 과금·용량 정책** = usage-based pricing.
- **기업 = 과금·쿼터 주체** (플랜별 월 토큰 상한 보유)
- **부서 = 집계·가시성 단위** (팀별 AI 비용 리포트)

## 1. 포지셔닝 (확정 — 제품/가격 통찰이 헤드라인)
**차별점은 제품 통찰이다. 억지 CS flex 없음.**
- 헤드라인: *"그룹웨어는 다 seat+GB 과금인데, AI 네이티브 제품이면 실원가는 토큰이다 → 잇다는 토큰 사용량 기반 과금 + 부서별 AI 원가 가시성."*
- 이게 강한 이유: ①원가구조를 이해한 제품감각(PO 시그널) ②데모데이 초기스타트업 청중 1순위=제품감각 ③안 무너지는 진짜 통찰.
- 기술은 **있는 것만 정직하게** 받침: 쿼터 상한 강제(정확한 소진 처리)·부서별 집계. 헤드라인으로 오버셀하지 않음.
- `job_id`는 방어적 중복 방지 키로만 유지(헤드라인 아님).
- 폐기: "멱등 미터링/이중청구 방지" — 요약 재생성 없음+성공 시 1회 이벤트라 막을 문제 자체가 없음(허위 flex).

## 2. 데이터 계약 (크로스도메인)

| 방향 | 상대 | 계약 | 내용 |
| --- | --- | --- | --- |
| IN(이벤트) | **A 캡처(이태연·김현지)** | `RecordTokenUsagePort` | 요약 **성공(READY) 시 1회** `record({companyId, teamId, meetingId, jobId, inputTokens, outputTokens, model})` |
| IN(체크) | **A 캡처** | `TokenQuotaPort` | 요약 **실행 전** `canConsume(companyId)` → 상한 초과면 차단/경고 |

## 4. 쿼터 강제
- 현재 기간 누적 = `SUM(total_tokens) WHERE company_id AND recorded_at ∈ 기간`
- **80% ≥ soft limit** → 경고(대시보드/알림) · **100% ≥ hard** → 신규 요약 차단(또는 overage 플래그)
- `canConsume(companyId)` = 누적 < 상한. A가 요약 전 호출.

## 5. 대시보드 (조립 읽기 뷰)
- 기업 월 총량 + **부서별 breakdown** + 회의별 drill-down + 상한 대비 게이지
- 인수인계 패키지처럼 **새 저장 아닌 집계 뷰**.

## 6. 데모 서사
*"회의 3개 하면 토큰 이만큼 → 개발팀이 이번 달 60% 소진 → 80% 넘으면 경고 → 100%면 신규 요약 차단."*
(이중청구 멱등 문구 삭제 — §1 참조)

## 7. 정직한 제약
1. **E 밖 두 번째 모듈** — 시간 예산(프리즈 8/13) 체크 필요. E 코어는 안정권이라 여유 있음.
2. **소유권 조율** — 용량/스토리지(ST)는 F(김현지) 인접. 토큰 미터링을 누가 소유할지 F와 정리.
3. **A 의존** — 파이프라인이 요약 성공 시 usage(input/output tokens)+jobId를 실제로 방출해야 함. 안 되면 목킹으로 데모(미터링 로직은 동일).
4. **실결제(Toss) 제외** — 측정·쿼터·대시보드까지. 카드결제 구현 안 함.
